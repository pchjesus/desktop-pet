# AI-Assisted Development Process 중간평가회 #1 회의록

## 1. 회의 개요

- 회의명: AI-Assisted Development Process 중간평가회 #1
- 프로젝트: 데스크탑 상호작용 펫
- 적용 Skill: AI-Assisted Software Development Skill v1.4
- 목적: AI와 함께 개발하는 과정에서 실제로 발생한 문제와 개선점을 정리하고, 향후 개발 프로세스와 Skill의 개선 방향을 결정한다.

---

## 2. 이번 평가의 기본 원칙

이번 평가에서는 문제가 발생했다고 해서 곧바로 새로운 규칙을 추가하지 않는다.

문제의 원인을 먼저 다음과 같이 구분한다.

- Skill의 부족
- 프로젝트별 지침의 부족
- 프로젝트 구조/문서의 부족
- 테스트 절차의 부족
- AI의 구현/판단 오류
- 사용자의 요구사항 전달 또는 해석 문제
- 개발환경/도구 문제
- 단순한 작업상의 실수

즉,

> 문제가 발생했다 → 규칙 추가

가 아니라,

> 문제 발생 → 원인 분류 → 적절한 계층에서 해결

을 기본 원칙으로 한다.

## 3. 실제 개발 과정에서 확인된 주요 문제

### 3.1 Electron / npm 설치 및 빌드 문제

초기 개발 과정에서 Electron 및 npm 설치 과정이 예상보다 많은 시간을 소요했다.

특히 다음과 같은 문제가 있었다.

- Electron 다운로드가 장시간 진행되거나 종료되는 문제
- 수동으로 파일을 준비했음에도 CLI가 다시 다운로드를 시도하는 문제
- npm 설치/재설치 및 경로 관련 문제
- Electron-builder 및 Windows 빌드 과정에서 발생한 환경/권한 문제

이를 통해 애플리케이션 코드 문제와 개발환경/설치/빌드 문제를 구분하는 절차의 중요성을 확인했다.

### 3.2 애니메이션 요구사항 해석 문제

캐릭터 애니메이션 구현 과정에서 사용자가 원하는 시각적 동작과 AI가 선택한 기술적 구현 방식 사이에 차이가 발생했다.

특히 사용자가 명시적으로 원하지 않은 접근과 유사한 구현이 반복 제안되는 문제가 있었다.

이를 통해 다음의 필요성이 확인되었다.

- MUST NOT 요구사항을 명확하게 추적
- 애니메이션/시각적 동작은 구현 전에 사용자에게 보이는 차이를 기준으로 확인
- 사용자가 명시적으로 거부한 접근을 반복 제안하지 않음
- 복잡한 캐릭터 행동은 최소 프로토타입으로 먼저 확인

### 3.3 테스트의 한계

AI가 수행한 자동 테스트가 통과하더라도 실제 프로그램 실행 환경에서 문제가 발견될 수 있었다.

예:

- 다른 컴퓨터에서 캐릭터 위치 또는 빈 공간과 관련된 문제
- 애니메이션, 창 위치, 드래그, 화면 경계 등 실제 실행 환경에서만 확인할 수 있는 문제

따라서 단순히 “테스트 PASS”라고 보고하는 것만으로는 부족하며, 어떤 범위의 테스트가 실제로 수행되었는지를 구분해야 한다.

### 3.4 AI의 특정 해결책 고착 문제

문제를 해결하는 과정에서 AI가 처음 선택한 구현 방향에 지나치게 고착되어 비슷한 방식의 수정이 반복될 가능성이 확인되었다.

이에 따라 다음 원칙을 중요하게 본다.

- 동일한 원인 가설에 기반한 수정이 연속으로 실패하면 같은 방식의 패치를 반복하지 않는다.
- 확인된 사실과 추측을 분리한다.
- 원인을 다시 재현하고 관련 코드/상태/환경을 다시 확인한다.
- 필요한 경우 다른 구현 방식이나 진단 방향을 검토한다.

### 3.5 파일 탐색 및 작업 시간

프로젝트가 커지고 파일이 많아질수록 AI가 기존 파일과 구조를 확인하는 데 시간이 증가할 수 있다.

따라서 앞으로는 무조건 지침을 추가하기보다,

- 프로젝트 구조를 단순하게 유지
- 필요한 정보를 적절한 문서에 기록
- AI가 매번 전체 프로젝트를 탐색하지 않아도 되도록 핵심 상태를 정리

하는 방향을 검토한다.

## 4. Skill v1.4에 대한 중간 평가

Skill v1.4에서는 다음과 같은 내용이 새롭게 강화되었다.

- MUST HAVE / MUST NOT 요구사항 추적
- 모호한 시각적/상호작용 요구사항의 사전 확인
- 의미 있는 구현 대안과 장단점 제시
- 동일한 원인 가설에 기반한 수정이 2회 연속 실패할 경우 재분석
- 환경/빌드 문제와 애플리케이션 코드 문제의 구분
- 구조 → 기능 → 통합 → 실제 실행/UX → 회귀의 계층적 검증
- 통합 테스트에서 오류가 발견되면 수정 후 재검증
- 실제 수행한 검증 범위를 명확하게 보고
- 구현 과정에서 발생한 workaround 및 불필요한 중복 코드 검토

현재는 이 내용들이 실제 개발에서 어느 정도 효과가 있는지를 관찰하는 단계이며, 아직 모든 항목이 충분히 검증된 것은 아니다.

## 5. 프로젝트 문서 구조에 대한 방향

Skill과 프로젝트별 기록을 서로 다른 역할로 유지한다.

### 공통 AI 개발 자료

프로젝트와 별도의 공통 폴더에서 관리한다.

```text
Common AI Development/
├─ AI-Assisted Software Development Skill v1.4.md
└─ 기타 공통 개발 자료
```

### 데스크탑 펫 프로젝트

```text
Desktop Pet Project/
├─ 실제 프로젝트 파일
├─ README.md
└─ Development-Reviews/
    ├─ Development-Review-01.md
    ├─ Development-Review-02.md
    └─ ...
```

Skill은 여러 프로젝트에 공통으로 적용되는 개발 방법론이고, `Development-Reviews/`는 해당 프로젝트에서 실제로 경험한 개발 과정과 개선 방향을 기록하는 프로젝트별 역사 기록으로 구분한다.

프로그램 버전, Skill 버전, 개발 프로세스 평가 기록은 서로 다른 축으로 관리한다.

- 프로그램 버전: 예) v0.7 → v0.8
- Skill 버전: 예) v1.4 → v1.5
- 개발 프로세스 평가: Review #1 → Review #2

## 6. 별도 Process Improvement Backlog 파일에 대한 결정

기존에는 향후 개선 후보를 별도의

`AI-Development-Process-Improvement-Backlog.md`

파일에 정리하였다.

검토 결과, 이 파일을 별도로 유지하면 회의록과 개선 후보가 중복되고 정보가 여러 파일로 분산될 가능성이 있다.

따라서 다음과 같이 변경한다.

### 결정

**별도의 Process Improvement Backlog 파일은 유지하지 않는다.**

앞으로의 개선 후보, 보류 사항, 추가 검토가 필요한 내용은 각 `Development-Review-XX.md`의 다음 평가회 검토 후보 항목에 기록한다.

이를 통해 다음 평가회에서 이전 회의록을 확인하면:

- 이전에 어떤 문제가 있었는지
- 어떤 개선을 검토하기로 했는지
- 무엇을 실제로 적용했는지
- 무엇을 보류했는지
- 무엇을 폐기했는지
- 새로운 개선점이 무엇인지

를 연속적으로 확인할 수 있도록 한다.

즉, 회의록을 **프로세스 개선의 단일 역사 기록**으로 사용한다.

## 7. 다음 평가회 검토 후보

현재 확정된 규칙이 아니라, 향후 실제 경험을 통해 필요성을 판단할 후보이다.

### 7.1 위험 기반 테스트

모든 기능을 동일한 수준으로 테스트하기보다 변경 위험이 높은 부분에 테스트 자원을 집중하는 방법을 검토한다.

### 7.2 프로젝트 구조 및 핵심 상태 문서

AI가 매번 많은 파일을 탐색하지 않아도 되도록 프로젝트의 핵심 상태와 구조를 간결하게 기록하는 방법을 검토한다.

예상 후보:

- README
- PROJECT_STATE
- ARCHITECTURE
- CHANGELOG
- TEST_CHECKLIST

단, 현재 바로 모든 문서를 추가하지 않고 실제 필요성이 확인될 때 도입한다.

### 7.3 리팩토링 및 중복 코드 정리 기준

일정한 기능 개수마다 강제로 리팩토링하기보다 다음과 같은 구조적 신호를 기준으로 정리하는 방법을 검토한다.

- 반복 코드 증가
- 함수의 과도한 복잡화
- 상태 관리 어려움
- 동일한 버그의 반복
- 기능 추가가 어려워짐
- 공통 로직의 과도한 결합

### 7.4 정기적인 프로세스 중간평가

개발이 충분히 진행된 시점마다 현재 프로세스를 다시 평가한다.

평가 대상:

- 실제 품질 향상 여부
- AI 오류 감소 여부
- 작업 시간 변화
- 파일 탐색 및 컨텍스트 부담
- 불필요하게 추가된 규칙
- 실제로 사용되지 않은 규칙
- Skill에 포함할 내용
- 프로젝트 지침에 남길 내용
- 별도 문서로 관리할 내용

### 7.5 평가회 역할 분담

향후 필요할 경우 다음과 같은 관점으로 평가할 수 있다.

- 코드/개발 관점
- 요구사항 확인 관점
- AI 오류 검증 관점
- 시간/효율성 관점
- 개발 프로세스 관점

실제 필요성이 확인되기 전까지는 역할을 고정하지 않는다.

### 7.6 작업 시간 및 효율성 측정

향후 개발 과정에서 다음과 같은 정보를 가능한 범위에서 기록하여 프로세스 개선의 근거로 활용하는 방법을 검토한다.

- 기능 하나에 걸린 시간
- 디버깅에 걸린 시간
- 파일 탐색에 걸린 시간
- AI의 잘못된 접근으로 추가된 시간
- 테스트 및 검증에 걸린 시간

정밀한 측정 자체가 개발 부담이 되지 않도록 필요한 수준에서만 기록한다.

### 7.7 Skill / 프로젝트 지침 / 프로젝트 문서의 역할 구분

같은 내용을 여러 곳에 중복 기록하지 않도록 다음 기준을 검토한다.

- 여러 프로젝트에 공통으로 적용되는 원칙 → Skill
- 특정 프로젝트에서만 필요한 운영 규칙 → 프로젝트 지침
- 현재 상태, 구조, 결정, 개발 이력 → 프로젝트 문서 / 회의록

### 7.8 지침의 압축 및 정리

규칙을 계속 추가하기보다 실제 경험을 통해:

- 추가
- 통합
- 압축
- 삭제

중 무엇이 적절한지를 판단한다.

특히 지침이 지나치게 길어져 AI의 컨텍스트 부담이나 작업 효율에 영향을 줄 가능성을 계속 관찰한다.

## 8. 회의록 작성 방식 자체에 대한 검토

현재 Skill v1.4에는 프로젝트별 개발 프로세스 중간평가회의를 정기적으로 기록하고, 각 회의록을 연속적인 역사 기록으로 관리하는 구체적인 절차가 별도로 정의되어 있지는 않다.

따라서 이를 즉시 Skill v1.4에 추가하지 않는다.

다만 여러 프로젝트에서 실제로 회의록 기반의 프로세스 개선이 유용한 것으로 확인된다면, **Skill v1.5에서 공통 개발 프로세스의 일부로 정식화할지 검토한다.**

향후 검토할 내용:

- 언제 평가회를 개최할 것인지
- 어떤 내용을 반드시 기록할 것인지
- 이전 회의록을 어떻게 다음 평가에 연결할 것인지
- 개선 후보의 상태를 어떻게 관리할 것인지
- Skill / 프로젝트 지침 / 프로젝트 문서에 어떤 내용을 반영할 것인지

핵심 원칙은 **회의록을 남기는 것 자체를 목적으로 하지 않고, 실제 개발 프로세스를 개선하는 데 도움이 되는 경우에만 제도화한다**는 것이다.

## 9. 향후 Skill 개선 방향

현재는 Skill v1.4를 실제 프로젝트에 적용하면서 충분한 경험을 축적한다.

다음 Skill 버전에서는 단순히 새로운 규칙을 추가하는 방식보다 다음을 중심으로 평가한다.

```text
실제 개발 경험
↓
문제 발생
↓
원인 분류
↓
해결 계층 결정
↓
반복 검증
↓
필요한 경우에만 Skill 수정
↓
불필요한 규칙은 압축/삭제
```

따라서 Skill v1.5는 v1.4보다 단순히 더 긴 문서가 되는 것이 목표가 아니다.

목표는 실제 개발 경험을 통해 검증된 내용을 남기고, 중복되거나 불필요한 내용을 정리하여 **더 효율적이고 재사용 가능한 공통 방법론**으로 만드는 것이다.

## 10. 다음 평가 시 확인할 사항

다음 중간평가는 파치리스 개발 이후 진행하는 것을 우선 목표로 한다.

주요 확인 사항:

1. Skill v1.4의 새로운 규칙이 실제로 도움이 되었는가?
2. 실제로 사용되지 않은 규칙은 무엇인가?
3. 새로운 규칙이 작업 속도나 파일 탐색 부담을 증가시켰는가?
4. AI가 명시적으로 거부된 접근을 다시 제안하는 문제가 줄었는가?
5. 구현 대안 제시가 실제 의사결정에 도움이 되었는가?
6. 계층적 테스트가 통합 단계의 오류 발견에 도움이 되었는가?
7. 통합 테스트에서 발견된 문제를 수정하고 재검증하는 과정이 안정적으로 작동했는가?
8. 프로젝트 구조/문서가 AI의 탐색 부담을 줄였는가?
9. Skill과 프로젝트 지침의 역할 구분이 적절했는가?
10. 회의록 기반의 프로세스 개선 기록을 Skill에 포함할 가치가 있는가?
11. Skill v1.5에서 추가할 것과 삭제/압축할 것을 무엇으로 결정할 것인가?

---

## 11. 이번 회의의 결정사항

### 확정

- Skill v1.4를 실험적으로 계속 적용한다.
- 현재 데스크탑 펫 프로젝트 지침을 유지한다.
- 프로젝트별 개발 프로세스 기록은 `Development-Reviews/`에서 관리한다.
- 프로그램 버전, Skill 버전, 개발 프로세스 평가 기록을 서로 분리한다.
- 별도의 `AI-Development-Process-Improvement-Backlog.md`는 유지하지 않는다.
- 향후 개선 후보는 각 개발 평가회 회의록에 기록한다.
- 문제가 발생했다고 해서 자동으로 새로운 규칙을 추가하지 않는다.
- 원인에 따라 Skill / 프로젝트 지침 / 프로젝트 문서 / 테스트 / 환경 / 구현 중 적절한 계층에서 해결한다.
- Skill v1.5는 실제 v1.4 적용 경험을 충분히 축적한 후 검토한다.
- 회의록 작성/관리 방식은 현재 v1.4에 즉시 추가하지 않고 Skill v1.5 검토 후보로 둔다.

### 다음 개발 목표

- 파치리스 개발 과정에서 Skill v1.4의 실제 효과를 확인한다.
- 기능 구현뿐 아니라 요구사항 해석, 대안 제시, 테스트, 통합 검증, 기존 캐릭터 회귀까지 관찰한다.
- 파치리스 이후 두 번째 중간평가회를 진행한다.

## 12. 회의 결론

이번 평가를 통해 확인한 핵심은 다음과 같다.

> 좋은 AI 개발 프로세스는 규칙을 많이 만드는 것이 아니라, 문제가 발생했을 때 그 원인이 어느 계층에 있는지를 정확하게 판단하고 적절한 곳에서 해결하는 것이다.

따라서 향후 프로세스 개선은

**추가 → 통합 → 압축 → 삭제**

를 모두 고려하며 진행한다.

Skill은 공통 방법론으로 유지하고, 프로젝트별 경험은 `Development-Reviews/`에 축적한다.

다음 평가회에서는 이번 회의의 기록과 실제 파치리스 개발 경험을 함께 비교하여 Skill v1.4의 효과와 개선 필요성을 평가한다.
